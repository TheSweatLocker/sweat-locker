### Root cause — three links, all measured

**1. A −4h EDT constant, in the one hour a day it is wrong.**
`nba_generate_props._et_today()` returned `(now_utc - 4h).date()`. In EST the
offset is 5h, so every run between 04:00 and 04:59 UTC returns **tomorrow** —
127 days a year. This is already documented in
`grade_public_receipts._et_shift_dst` and in `sweat_dates`; this file just
never used either.

The 22:41 UTC cron landed at **04:21 UTC** (GitHub cron lateness, documented
in `nba_props_refresh.yml` itself). `_et_today()` said 2026-11-26; the ET date
was still 2026-11-25. Both West-coast games were **in progress at that
moment**. 210 rows written onto a slate that does not exist.

The stamp was wrong twice over: the event filter accepted a UTC prefix of
`gd` *or* `gd+1` — correct in principle, since a late ET game commences on the
next UTC day — and then stamped every surviving row with the single global
`gd`. When `gd` was a day ahead, the filter and the stamp were wrong together.

**2. A NULL never reached the gate.** Those rows carry an Odds-API event id,
while `nba_game_context` carries ESPN ids. The card's kickoff filter needs a
start time, found no context row, and had nothing to judge — so it passed
them. `feedback_a_null_never_reaches_a_gate`.

**3. The floor shipped yesterday pulled them in.** The card was short, so the
`CARD_FLOOR` ladder refilled to its weak floor of 3 from the prop rung. The
floor's refusal list checks "game already played" **only for non-props**
(`if not is_prop and cg in have_games`), so a dead prop was never refused.
The floor did exactly what it was built to do, with poisoned candidates.

### Fixed

- `nba_generate_props.py` + `nhl_generate_props.py` (identical bug, same
  function, same line): `_et_today()` now delegates to `sweat_dates.et_today()`
  (zoneinfo, DST-correct), falling back to −5h — erring toward the *previous*
  ET day, because a day behind fetches an empty window and says so while a
  day ahead stamps finished games as upcoming. New `_et_date_of()` derives
  **each row's** `game_date` from its own `commence_time`, so the stamp cannot
  inherit an error from the runner's clock.
- `generate_sweat_card.py`: new `tonights_games()` / `prop_rows_on_slate()`.
  Both prop feeders — `fetch_nba_prop_floor` and `_fetch_non_mlb_props` — now
  resolve the slate from the **context table** instead of trusting
  `game_date`, and a prop must name a game still to be played. Games whose
  start time has passed are excluded, so a prop on a finished game is
  off-slate even when the rest of its night is live.

  Verified against today's real data: 210 phantom rows → **0 kept**;
  `fetch_nba_prop_floor('2026-11-26')` returns **0 candidates** instead of two
  dead props.

**Scope is deliberate.** The guard covers the prop feeders and nothing else:
prop `matchup` holds full team names in every per-sport props table, matching
the context columns, whereas a POTD label carries abbreviations ("KC @ BUF")
that would not join. Guarding the card generally would have risked refusing
the POTD.

**Two calibrations that came out of testing the guard, not out of theory:**

- NHL props write `"St Louis Blues"` where `nhl_game_context` writes
  `"St. Louis Blues"`. That one period refused a real NHL game of 14 on both
  11-21 and 11-25. `_norm_mu` now drops periods — narrow on purpose, because
  it cannot merge distinct teams ("michigan st" stays distinct from
  "michigan"), and that case is pinned.
- **An unreadable slate passes rows unchecked.** Refusing on a context
  outage would empty the prop path on every card for as long as the read
  fails — a far bigger blast radius than the defect. `tonights_games`
  returns an empty set for "plays nothing" and `None` for "could not read",
  and those are different answers. `feedback_a_guards_blast_radius`.

## 5. "High probability plays" — the bar is the problem, and here it is

`ncaab_game_results` has no spread-odds or total-odds column at all. So a
spread or total signal is scored against a side baseline, which is not a
price. Measured this season:

```
NCAAB 2026-27 direction-only base rates
  totals  n=965   OVER 50.6%   UNDER 49.4%
  spread  n=961   HOME 48.7%   AWAY 51.3%
  ml      n=1350  HOME 76.4%   AWAY 23.6%

  THE FAVOURITE wins straight-up 72.8% (n=913 priced games)
  median favourite price -259  ->  breakeven 72.1%
```

Against those bars, the engine's maximum-weight signals look very different:

* **`OFF_RATING_GAP` ml, 75.41% on n=423, weight 1.0.** The registry calls

  SAME games against the spread reads **50.32% on n=157** and gets weight 0.0.
  A 75% moneyline rate paired with a 50% spread rate is the signature of a
  favourite detector, not a handicapping edge.
* **`ncaab_home_shooting_edge` ml 69.3% (n=238)** sits BELOW the 72.1%
