# 2026-10-14 — CI failure fixed, issue log revised

## The NFL Pipeline Weekly failure: a false failure

Run **38503899770**, 2026-10-14T03:03 UTC. `workflow_heartbeat` had the step
and the return code: `refresh_nfl_team_features.py`, rc=1, 29s.

**The write succeeded. The verification was wrong.** All 193 rows got
`features_computed_at = 2026-10-14` (UTC). The check compared

```python
str(x.get('features_computed_at'))[:10] == et_today()
```

and `et_today()` returned **2026-10-13**, because the stamp is written in UTC
(`dt.datetime.now(dt.timezone.utc)`) and compared against an **Eastern**
date. Between 00:00 and ~04:00 UTC the two disagree by a calendar day and
every row looks unstamped → `stamped=0` → `return 1`.

The `0 */6 * * *` cron puts one run in that window every night, which is why
it failed nightly and passed during the day — the shape that reads as flaky
rather than wrong. The run fired at 02:59 UTC = 22:59 ET.

**Fixed** by comparing against the run's own timestamp with 2h slack instead
of a calendar day. A date comparison is the wrong instrument regardless of
which timezone wins — a job straddling midnight would fail it too. Verified:
193/193, exit 0.

**Also fixed in the same file:** the PATCH loop ignored its own status code.
The verify block opens with *"A 204 is not a write — prove it landed"* and the
write it was proving was unchecked, so a PGRST204 or an auth failure returned
silently and the only symptom was the verify reporting 0/N — which reads as a
stamp problem, not a write problem. Now counted and reported.

Scanned for the same `[:10] == et_today()` pattern repo-wide: this was the
only instance.

## FIXED — market sanity, every sport

New `watchdog_market_sanity.py`. The same defect keeps recurring: a value that
is not a line at all, sitting in a line column.

| where | what was stored |
|---|---|
| `nhl_game_results.close_puckline` | moneyline prices on 1,120 rows, `0.0` on 3 |
| `nfl_game_context` CHI @ CAR | `close_total` 96.5 / `close_spread` −21.5 on a 59-37 game |
| `mlb_game_results` | `close_spread` 4.5–15.5 on 10 April rows |

**The MLB set was new tonight and 8 of the 10 had a `spread_result` graded off
the bogus line.** Worst case: BOS @ BAL finished **17-1** (18 points, margin
16) carrying `close_spread=15.5`, `close_total=18.5`.

The watchdog detects the condition rather than the cause, because the cause is
still unknown — static search found nothing deriving a line from a score, so
"a bad odds-feed row" is still live against "a results-to-context writer".
Guessing and patching the wrong script would leave the real one running.

- `--repair` copies a plausible value from RESULTS onto an implausible CONTEXT
  row. Never the reverse: results is the graded source of record.
- `--null-unfixable` NULLs a results value where nothing cleaner exists, plus
  any grade **reproducible from** the bogus value (which proves it was derived
  from it). Per `backfill_game_grades`: *a wrong grade is worse than a missing
  one because it looks like evidence.*
- Bands mirror `backfill_game_grades.SPORTS` for NHL/NBA/NCAAB so the two
  cannot drift. MLB's low end is set at 5.5 because the 1.5/2.5/3.5/4.5 values
  found in `close_total` look like `f5_total_line` (first five innings) written
  into the full-game column.

**Result: 5 of 6 sports now clean.** 24 MLB rows nulled. NFL has 4 remaining —
3 preseason rows with no results row to repair from, and one frozen opener.

Wired into `nightly_cross_sport.sh` with `--repair`, deliberately NOT
`--strict`, so a pre-existing row cannot start failing the nightly.

## FIXED — `div_game` was 0% on the 2026 NFL season

Populated on 285/285 in each of the last five seasons, **0 of 274 in 2026**
(79 already played). Cause: the forward schedule is now created by
`nfl_odds_pull` via `odds_pull_core.build_rows`, which writes market columns
and nothing sport-specific; the historical rows came from the results
importer, which did set it.

It matters because `div_game` feeds the model and the `nfl_div_home_cover`
cohort, and a NULL reads as "not a division game" to any truthiness test — a
**wrong** feature, not a missing one.

`backfill_nfl_div_game.py` fills from `nfl_game_context.NFL_DIVISION`,
imported rather than copied (four copies of that map already exist, and a
fifth is how they drift). **Deriving from history would have been wrong:** a
team's historical division rivals span realignment, so Arizona comes back with
both NFC East and NFC West and the derived map claims 35 teams. Guards on the
derived division share (refuses outside 18–45%); measured **35.0%**, and 6
division games in a 17-game schedule is 35.3%. **274/274 filled, 0 NULL
remaining.** Wired into `nfl_pipeline.yml`.

## NEEDS ANDY — `20261014a_opening_line_repair.sql`

`freeze_opening_lines()` preserves any non-NULL `open_*` unconditionally, so a
corrupt opener is immortal: no UPDATE can change it, **not even to NULL**, and
PostgREST returns 200 while handing back the old value. CHI @ CAR still holds
`open_total=96.5`.

The migration adds the one sanctioned override: a SECURITY DEFINER RPC
(`repair_opening_line`) with a function-scoped
`SET sweat.allow_open_override = on`, which the trigger honours and nothing
else sets. One table, one game_id, whitelisted table names, NULL args left
untouched.

**Rejected the simpler option** of letting `NEW.open_x IS NULL` through:
PostgREST batch upserts union their keys across rows, so a batch where only
some rows carry `open_*` sends `open_total: null` for the rest
(`feedback_postgrest_batch_normalize_keys`) — turning an accidental key union
into a silent mass erase of real openers. Worse than the bug being fixed.

`watchdog_market_sanity` already calls the RPC and reports
`repair_opening_line does not exist yet. Apply 20261014a` until it is applied.
