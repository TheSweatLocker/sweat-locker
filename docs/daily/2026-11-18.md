### 1 · The Sharp "placement problem" was the lock working — the detector was wrong

Took this first because 11-17 §8.11 logged it for "tomorrow with the board
quiet", and at 03:00 ET that is now. **It is not a placement problem**, and
the full correction is written up at **11-17 §8.14**. Short version:

`generate_sharp_card` hard-locks at **12:00 ET** and refuses a republish
*"regardless of `--force`"*, quoting Andy's 09-19 directive *"whatever
comes out in the morning stays."* The card published **10:41 ET**; the
21:09–21:49Z `mlb_pipeline` run was **16:09–16:49 ET**, so it correctly
refused to rebuild. Had I "fixed the placement" I would have been
dismantling a lock Andy asked for twice.

The real defect was in the detector. `check_card_integrity` check 1 said
*"the card must agree with the engine as it stands NOW"* — wrong by
construction once the card is frozen and the engine keeps re-deriving.
`line_history` proves the card's `Over 130.5` was a live, widely-posted
number at publish (fanduel 13:28Z, espnbet 14:26Z) and the market only
drifted to 128.5 afterwards (draftkings 14:54Z, espnbet 17:26Z, betmgm
20:57Z). A lag, not a disagreement.

**Fix shipped.** Severity on the engine-comparison checks now depends on
whether the finding is still *actionable*:

| when | severity | why |
|---|---|---|
| before the surface's hard lock | **FAIL** (gating, exit 1) | the card can still be rebuilt |
| at/after the lock | **drift** (reported, non-gating) | republish is refused, so a FAIL is noise |

Keyed on the **card's date**, not the bare clock — a past slate is locked
at every hour, so checking yesterday's card at 3am must not report FAILs.
Checks about the frozen artifact being wrong *on its own terms* — juice
traps, prose naming the other team, a spread with no line — stay **FAIL at
every hour**, because those are defects in what we published rather than
drift away from a moving reference.

Re-run on last night's card: **FAIL 4 → FAIL 0 · warn 2 · drift 4**,
exit 0.

A `--self-test` pins the clock and asserts **both** directions (5/5
passing) and now runs in `daily_card.yml` ahead of the real check — a
regression that made the rule always return DRIFT would otherwise
silently disable the detector with nothing in CI noticing.

Independent confirmation the engine churns while the card is frozen: the
Vanderbilt row read `total` / `Under 147.5` at 19:30 ET and reads `ml` /
`Vanderbilt ML` at 03:00 ET — three distinct engine states for one card.

**Method note, worth keeping:** §8.11 concluded "the step never ran" from
`generate_sharp_card` being absent from `step_durations` meta. That meta's
`steps` field is an **integer count**, not a list of names, so the absence
proved nothing — a wiring error dressed as a finding. Printing the field's
type is what caught it.

### 2 · The NBA prop receipt anchored on the GAME, not the prop

Carried-in item: *"writer stores `prop:<game_id>` where a prop id
belongs."* Root-caused and fixed at both ends.

**The two live rows** (frozen, already graded correctly via last night's
grader workaround):

```
5507438  NBA sweat_card 11-16  source_id='prop:39dbdb7fdc78bd01ceac2fc7048bc1fd'
         'Meleek Thomas PTS UNDER 12.5'  player_name NULL  prop_type NULL  WIN
5507439  NBA sweat_card 11-16  source_id='prop:a613d212acef6f86d71b6ef99049fb7b'
         'Cam Spencer PRA UNDER 24.5'    player_name NULL  prop_type NULL  LOSS
```

Both 32-hex values are `nba_pipeline_props.game_id`. `audit.captured_by`
named the writer: `generate_sweat_card`, section `unified_top_picks`.

**The chain.** `public_receipt._card_anchor` resolved a prop's identity as
`source_key or game_id or id`. `fetch_nba_prop_floor` — the one NBA cell
measured positive, used to fill the card floor — emitted a dict with **no
`source_key`** and **no `id`** (its props-row id sat under the private
`_prop_id`). So the chain fell through to `game_id`.

That is the exact failure `_card_anchor`'s own docstring warns about:
*"Props keep source_key, which carries 'player|prop_type|line'; a game_id
would collapse every prop in a game into one row (the defect fixed on
10-04)."* **Two NBA props in one game would have become one receipt, and
one of the two bets would have vanished from the ledger.** It also
explains the NULL `player_name` / `prop_type`: the parse at
`public_receipt.py:1245` reads both out of `source_key`, and there was
none to read.

Same family as the 11-15 NFL leg whose own backfill audit says *"the
measured-cell prop path emits `market='prop'` with no type key, so this
leg published with no receipt"* — a measured-cell path emitting a
different dict shape than the main path.

**Fixed at the producer:** `fetch_nba_prop_floor` now emits
`source_key = "{player}|{prop_type}|{prop_line}"`, plus `id` and
`prop_line`. Verified against live data — it reproduces the two 11-16
picks exactly, now as `Meleek Thomas|pts_under|12.5` and
`Cam Spencer|pra_under|24.5`, the standard pipe-composite the grader
already handles natively, with player and type populating.

**And at the chokepoint,** because a guard on one of eight sources is not
a guard. For a prop, `_card_anchor` now prefers the props-row id over the
game and **refuses a bare `game_id`**, falling back to
`game|label|line` — which still distinguishes two props in one game — and
printing a loud warning naming the producer to fix. Exercised on seven
shapes: MLB-with-source_key unchanged, sides still anchor on `game_id`,
the `fade:401909281:rl` three-part strip still works, and two props in one
game now resolve **distinct**.

The warning text is deliberately ASCII: it runs inside a receipt writer,
and a cp1252 stdout raises `UnicodeEncodeError` on a decorative glyph —
caught in test, because a log line must never be able to kill a publish.

**Not touched:** the two existing receipts. Identity columns are frozen,
they are already graded correctly, and the grader keeps its bare-32-hex
path for exactly these rows. **Follow-up noted, not done:** the dict still
has no `prop_type` key, so `prop_publish_lock` skips these picks (the
`_market` detection at `generate_sweat_card.py:~5890` reads `prop_type`).
Adding it would bring them under the tier/conviction freeze — correct, but
it changes lock behaviour and did not belong in a 4am change.
