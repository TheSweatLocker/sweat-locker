## POTD: why it was recorded wrong, and what now catches it

The parser hole is fixed (match a spread by **shape**, not by looking for the
words `rl`/`ats`/`spread`, which a basketball line does not carry). But three
separate things meant nothing would have caught it:

1. **`verify_potd_coverage.py` was in no workflow.** The script whose entire
   job is POTD integrity only ran by hand. Now a step in `daily_card.yml`,
   right after the anchor that writes the pick, `--warn-only`.
2. **It treated `no-pick` as terminal**, so it would have passed on the
   Raptors row regardless — a Win stored as "we did not play" was invisible to
   it. `no-pick` is now only terminal when the lean does not name a play.
   Self-tested on 11 lean shapes, 0 failures.
3. **It crashed on its own first finding.** Cross and box-drawing glyphs
   against a cp1252 Windows console raise `UnicodeEncodeError` on the very
   line about to say what was wrong. CI never saw it because the workflow sets
   `PYTHONIOENCODING`.

Two defects it found immediately:

- **`Void` was missing from `TERMINAL`**, so 10-16 (Nick Martinez Over 3.5
  Hits Allowed, Void) was reported as "still ungraded after the games
  finished" — and would have been forever, since nothing can grade a bet that
  never ran. `grade_potd` has always treated Void as settled; the checker
  disagreed with the grader.
- **The writer defect behind 10-10.** `play_of_day.py:4932` falls back to
  `"<away> @ <home>"` when `lean_display` is missing, so the field holding the
  **pick** received a **matchup**, which propagated to
  `daily_best_bet_history.lean` — what the calendar renders and what
  `grade_potd` parses. Added `leanIsMatchupFallback`; the checker uses a
  **shape** test rather than that flag, because the flag only exists on rows
  written from today on and the history has to be caught too.

Deliberately did **not** recover 10-10 by parsing the narrative. Its headline
is `Chicago White Sox @ Cleveland Guardians ML` — that names no side, and only
the prose says "back the away side." Inferring a side from prose on a bet is
how a loss gets booked as a win.

**POTD now: 81-65-4 (55.5%), 0 pending, checker reports consistent.**

## NBA opening lines: spread and total work, the moneyline had no column

Andy: *"opening lines i dont thinkare showing ... line moevemnt is improtant
for nba"*. Checked the three rows of that strip separately.

**Spread and total are working.** `preserve_opens()` was added to
`nba_game_context` on 10-20 and records an opener correctly — first sighting
wins, never overwritten, frozen by a DB trigger. On rows that have odds the
openers are there and they are moving:

| | moved off its open |
|---|---|
| spread | **3 of 14** — DAL −10.5→−9.5, UTA −2.5→−1.5, CLE −2.5→−3.5 |
| total | **6 of 14** |

Games two and three days out show nothing because they have **no odds yet** —
`close_spread` is NULL on 10/23 and 10/24, and an opener cannot be recorded
from a line nobody has posted. That fills in by itself.

**The moneyline row could never render.** The client reads
`ctx?.home_ml_open`, and that column **does not exist** on
`nba_game_context`. Probed per column rather than inferred, because this
schema has two live conventions:

| table | opening-ML columns |
|---|---|
| `mlb_game_context` | `home_ml_open` / `away_ml_open` |
| `nhl_game_context` | `home_ml_open` / `away_ml_open` |
| `ncaab_game_context` | `home_ml_open` / `away_ml_open` |
| `nfl_game_context` | both conventions |
| **`nba_game_context`** | **neither** |

NBA was the only gap, so that row has read "no open" on every NBA card since
the sport went live. `20261022a` adds `home_ml_open`/`away_ml_open` — **that
exact name, because the shipped client already reads it**, so the opening
moneyline appears with no build. `preserve_opens` now mirrors them on first
sighting alongside spread and total.

The freeze trigger needs no change and I checked why: `freeze_opening_lines()`
iterates a hardcoded array already carrying both conventions and guards each
with an existence check, so the new columns fall under the existing
BEFORE UPDATE trigger automatically. That trigger is also why the writer must
only mirror into an empty slot — it discards a correction and still returns
200.
