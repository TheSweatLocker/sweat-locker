### 3. `reconcile_ncaaf_duplicate_games.py` — one game, one row

Groups by `(game_date, canonical team PAIR unordered)` so an inverted
home/away lands in the same group, picks the scored row as survivor, merges
every non-null field from the losers, deletes the losers.

Dry run on 2026: **would merge 6, held 17.**

It refuses to touch a group where:

- two rows carry **different scores** — a disagreement about what happened,
  not a duplicate;
- orientation is **inverted and both rows scored** — merging would decide
  which feed is right about who was home, and on a spread that flips the side;
- a row due for deletion is referenced by a **graded** receipt or read —
  deleting it orphans a published claim.

That last guard is why 17 are held, and it is also the finding: both twins
often have graded receipts.

Also surfaced a fourth duplicate flavour I had not seen — **date-adjacent
twins** one day apart (`ncaaf_20260918_Portland State_Oregon` vs
`..._20260919_...`, Georgia/Alabama on `20261010` and `20261011`). That is the
UTC-vs-ET id bug fixed for new pulls on 09-16, leaving historical twins
behind. Grouping on `game_date` rather than the id's date catches them.

**Not applied.** It deletes rows; that is Andy's call.

## The duplicate factory, closed at source

`_sweep_ungraded_jerry_reads` in `resolve_ncaaf_results.py` was minting them.
Its docstring says *"Idempotent: skips jerry_reads whose game_ids already
have a ncaaf_game_results row"* — and that check is on the **game_id**, not
on the **game**. Since the id is composed from team names, a jerry_read
carrying one spelling against a results row written under another makes
`gid not in existing_ids` true, and the sweep upserts a second row for a game
we already have.

Now it looks the game up by **date + folded team pair, unordered**, before
inserting:

- **unordered** because the one genuinely dangerous duplicate is Oklahoma @
  Texas — a neutral-site game where home and away are swapped between the
  rows. An ordered key misses exactly that case.
- if the twin **already has the score**, it does not insert. The read stays
  ungraded and the log names both ids, because an ungraded read is visible
  and fixable while a duplicate row is neither.
- if the twin exists but is **scoreless**, it fills that row rather than
  minting a third id for the same game.

Verified against the real table rather than assumed: the guard's key groups
**26** duplicate groups out of 639 rows, including the inversion and the
`UMass` / `Massachusetts` pair. All 26 would have been prevented.

Today's dry run: `reverse-sweep: 0 upserts from 17 ungraded jerry_reads` — the
guard doesn't fire because there is nothing to duplicate today, i.e. no
regression on the normal path.

**The id disagreement itself is still open**, and the log now says what to do
about it: either repoint the `jerry_read`, or make `grade_jerry_reads` try the
key variants this module already builds for its own lookups (~line 714). That
is a decision about a published row's join key, so it is Andy's.
