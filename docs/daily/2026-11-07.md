## Supabase disk IO budget depletion warning — ROOT CAUSE FOUND

Andy got a Supabase email: the project is projected to deplete its disk IO
budget. He asked what changed.

### The flood

`supabase_logs (14).json` — a continuous stream of

```
23505  duplicate key value violates unique constraint
       "public_receipts_live_source_uniq"
```

at 19:59 UTC on 11-06, one roughly every **80 ms**, for the length of the
window. 80 ms is a serial per-row HTTP POST round trip, so this is a loop,
not a burst.

### Root cause: the dedupe was testing membership against a TUPLE

`a07631aa` (10-31, "Last night's 5-0 was recorded as 7-0") changed
`public_receipt._live_keys()` to return **two** sets — `(source_id keys,
bet keys)` — so one wager recorded under two source_ids could be caught.

`capture()` was updated to unpack it:

```python
existing, live_bets = _live_keys(payload)
```

`backfill_public_receipts.py` was **not**:

```python
live = _lk(rows)                                   # a 2-TUPLE of sets
fresh = [r for r in rows if (sport, surf, date, src) not in live]
```

`x not in (set_a, set_b)` asks whether the 4-tuple *equals* one of the two
sets. It never does. So the test was True for every row and **the dedupe has
been a no-op since 10-31**.

Replayed against 400 receipts that already exist in the table:

| | rows POSTed | result |
|---|---|---|
| shipped 10-31 → 11-07 | **400 of 400 (100%)** | 400 rejected INSERTs |
| fixed | **0 of 400 (0%)** | no POST at all |

Every run POSTed its entire reconstructed history. The batch INSERT is
all-or-nothing, so it took 23505 on the first already-existing row, fell
back to per-row, and then wrote one *rejected* INSERT per historical
receipt. A rejected INSERT still writes a heap tuple and a WAL record and
leaves a dead tuple behind — so this burned disk IO and autovacuum capacity
on writes that could never land.

Measured, MLB alone: **1,028 rejected INSERTs per run.** Runs in
`daily_card.yml` for **7 sports × 3 crons a day**.

### Second defect: the window in the comment did not exist

`daily_card.yml` said of the step:

> A 7-day window keeps it cheap; the historical sweep is a manual
> `--since` run.

There was no `--since` flag and no window. `main()` parsed only `--sport`,
`--source`, `--dry-run`. Every run reconstructed **every game ever**, for
all 7 sports, 3× a day.

That costs read IO too, independent of the write bug: `_live_keys` pages
`public_receipts` once per `(sport, surface, game_date)` group, so a
full-season MLB `sharp_card` payload alone issues ~180 GETs — per source,
per sport, per run — to re-confirm rows frozen months ago.

### Fixes

1. **`backfill_public_receipts.py`** — unpack the tuple, and apply the
   same-bet-different-source_id check `capture()` already made. Prints the
   denominator every run (`N reconstructed, M already live, K to write`) so
   a silent `return 0` can't hide a repeat (`feedback_green_step_that_writes_nothing`).
2. **`--days` / `--since`** at the `upsert_batch` chokepoint — the one place
   all 8 sources pass through, same as the future-date guard
   (`feedback_guard_belongs_at_the_chokepoint`). Script default stays
   **all history**, so a manual sweep is unchanged; only the scheduled run
   passes `--days 14`.

## The fill scan cried wolf twice before it was trustworthy

Both false positives were mine, and both are worth recording because they are
the exact failure modes I spent the day finding in other people's code.

|---|---|---|---|
