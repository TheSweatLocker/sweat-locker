## Fixed today

### The Dawg graded the wrong game (user-facing)

`daily_dawg` 10-28 NHL **Seattle Kraken ML +117** stored `result='Loss'` and
`final_score='Milwaukee Brewers 4 @ Tampa Bay Rays 1'`. Seattle **won 5-4**.
The receipt had it right (WIN); the Dawg table was wrong, and
`sync_receipt_grades` has been reporting it as a conflict since.

One assumption, three defects in `resolve_game_results.py` — until 10-28
there was exactly one Dawg a day and it was always MLB:

1. `PATCH daily_dawg?game_date=eq.{date}` (three call sites) hit **every**
   sport's row on that date, so the MLB row's grade and score were stamped
   onto the NHL row.
2. Scores were read only from `mlb_game_results`, so a non-MLB Dawg could
   never find its game and fell through to the MLB-API-only postponed /
   self-heal path.
3. `dawg['team']` is now `'Seattle Kraken ML'` (the generator writes
   `call_text`), so the team-**name** equality test can never match. Two
   independent reasons it would have said Loss.

Fixed: PATCH by `id`; grade from the `jerry_read` the Dawg was lifted from
(`signals.jerry_read_id`) when it still agrees on side **and** market, else
from that sport's own results table using `pick_side`; MLB-API paths gated to
MLB; a non-ML Dawg is left pending rather than graded on the ML rule.

Added `--regrade-dawg=YYYY-MM-DD`, because the normal pass only sees
`result IS NULL` — a *wrong* grade had no repair path. Extracted the block
into `_resolve_dawgs()` so the repair touches nothing else. Re-derived:

```
🐕 2026-10-28 [MLB] Tampa Bay Rays ML  → Loss (from read 13073)
🐕 2026-10-28 [NHL] Seattle Kraken ML  → Win  (from read 11196)
```

Read back: `Toronto Maple Leafs 4 @ Seattle Kraken 5`, result Win.

I also flagged a 10-08 MLB Dawg as mis-graded and that was **wrong on my
side** — that row has `pick_side` NULL, and my check treated NULL as AWAY.
White Sox were home and lost 5-9; `'Loss'` is correct.

### The flip-price window had no server-side ceiling

`_flip_prices` in `generate_sharp_card.py` computed `hi` and applied it only
in Python. The server saw `commence_time >= today` with no upper bound and
`ORDER BY captured_at DESC`, so it sorted every future-scheduled
`line_history` row and returned

```
HTTP 500 57014 canceling statement due to statement timeout
```

on NCAAF. The function reports that and returns `{}` — and no flip prices
reads as "no book posts the other side", so both NCAAF flip candidates were
dropped and today's Sharp composed **0**. Added `lt.{d0+3d}` to the server
filter, one day past the Python ceiling so it can only discard rows Python
would discard anyway.

```
before: two-sided quotes found: 0   TOTAL=0
after:  two-sided quotes found: 8   TOTAL=2   {'NCAAF': 2}
```

Both are short-spread flips in the validated ≤10.5 band (our side of that
band is 4-18, n=22).
