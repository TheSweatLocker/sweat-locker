## The migration that came back broken, and what I changed about how I work

`20261029a` failed its first paste with **42P10** — `ON CONFLICT
(signal_key)` names a key `signal_sources` does not have. The table declares
`UNIQUE (signal_key, sport, market_scope)`; 20260820 added
`(signal_key, sport)` only conditionally. 20260911c and 20260818 both hit
this exact thing and both switched to a NOT-EXISTS guard.

Andy: *"if you give me broken migrations how can i trust you are doing the
right thing in building an engine that actually works"*

The specific failure is worth naming precisely, because the two halves were
not verified to the same standard. That migration's **expressions** were
replayed through `signal_expr` against live ctx rows before shipping — 4/4,
fire on a good ctx, False on a blank one. Its **DDL was only read**. Reading
cannot catch a 42P10, because the answer lives in `pg_constraint`, not in
the file.

Verified the failed paste rolled back whole before changing anything: all 14
columns still `42703`, zero rows at that origin. Nothing half-applied.

Rewrote to `INSERT … SELECT … FROM (VALUES …) WHERE NOT EXISTS`, which has
**no conflict target at all** — 42P10 is impossible by construction, under
any index configuration. Then verified the catalog claims it still makes:

```
all 12 inserted columns exist on signal_sources   -> 200
negative control (bogus_col_xyz)                  -> 400 42703
class/enabled types confirmed on a live matchup row
the 6 signal_keys currently present               -> 0  (all 6 will insert)
live ON CONFLICT clauses remaining                -> 0  (both hits are comments)
```

**New: `mlb_pipeline/validate_migration.py`.** Runs a migration against the
live schema inside a transaction it then unconditionally ROLLS BACK, and
reports the real SQLSTATE. Full mode needs a DB password, which is **not in
this repo** — not in `.env`, not in GH secrets, only the pooler host in
`supabase/.temp/pooler-url`. Until that exists it falls back to
`--parse-only` (sqlglot) and **says on every run** that syntax checking
cannot see the catalog, so it cannot catch a 42P10. Proof of that honesty:
parse-only gave byte-identical output for the broken and fixed files.

Two bugs caught in the validator by its own self-tests:
* sqlglot rejects `COMMENT ON COLUMN … IS 'a '\n'b'` — Postgres merges
  adjacent literals across a newline and sqlglot does not. Added
  `merge_adjacent_literals`; a checker that is wrong about the intentional
  case gets ignored.
* My newline test was tautological (`'\n' in x + '\n'`), so same-line
  `'a' 'b'` — a Postgres **syntax error** — was being merged and hidden.

What it does NOT prove: that a migration is *correct*. It can execute
perfectly and seed a signal that fires on the wrong side. Correctness still
needs the measurement.
