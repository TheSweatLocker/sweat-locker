## 🚨🚨 RLS: the anon key can WRITE (incl. public_receipts)

The serious finding of the day, and it outranks the IO work.

RLS is disabled across the public schema. The anon key ships **inside the app
bundle** and can be read out of any installed copy. It is not limited to
reading — it can write. Verified from outside with the shipped key, using
DELETE and PATCH with a filter matching zero rows (nothing altered), getting
200/OK instead of 401/403 on:

| relation | why it matters |
|---|---|
| `public_receipts` | **the public graded record** — the whole "we show the receipts" brand |
| `prompt_templates` | the LLM prompts |
| `feature_flags` | what the app turns on |
| `sweat_tier_config` | the tier gates |
| `user_note_dispatch_log` | carries `user_id`, 1,070 rows |

Anyone able to UPDATE `public_receipts` can silently rewrite the record.

### Two measurement corrections, both mine

1. **First write probe was invalid.** I probed with a non-existent column and
   read 400 PGRST204 as "the privilege check passed." It does not: PGRST204
   comes from PostgREST's own schema cache, which rejects the payload before
   any SQL reaches Postgres. Re-ran with a zero-row DELETE/PATCH, which does
   reach the database.
2. **I over-called `user_notes`.** I described it as user data with 310 rows.
   It has no user columns at all — title/body/category/cohort/severity. It is
   broadcast notices the app is supposed to read. The real exposure is
   `user_note_dispatch_log` (`user_id`) and `prompt_templates`.

### Fix: `20261021c_rls_close_anon_writes.sql` — NOT YET APPLIED

Structured so it is read-neutral and write-closing, because there is no OTA
path and a broken read cannot be hot-fixed:

- **A** — every relation the client reaches via `.from()` (76), plus
  `ufc_picks`, which appears in **no** `.from()` call and is reachable only
  through `get_todays_ufc_picks()`. All four client RPCs carry no
  `SECURITY DEFINER` clause, so they run as SECURITY INVOKER with the
  caller's privileges; a table reached only through one still needs a read
  policy or that tab goes dark. RLS on + permissive SELECT → reads unchanged,
  writes denied (RLS default-denies any command with no matching policy).
- **B** — `user_note_dispatch_log` and `user_consent` are written by the
  client and never read back, so they get INSERT/UPDATE and **no** SELECT.
  Closes the `user_id` read exposure while keeping dismissals working.
- **C** — every other public table: RLS on, no policy = anon denied outright.
  `public_receipts` and `signal_attribution` land here. Safe because no
  migration anywhere sets `security_invoker`, so the `v_*` views run as owner
  and base-table RLS does not reach them — the view-backed tabs keep working.

Applied through a `DO` block checking `pg_class.relkind`, because 7 of the
listed relations are views and `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` on
a view is an error. Part C handles `insufficient_privilege` per table so one
extension-owned table (PostGIS `spatial_ref_sys`) cannot abort the block and
silently leave everything after it open.

The pipeline is unaffected: service-role bypasses RLS, and the one edge
function (`odds-proxy`) uses service role. No auth in the app at all — zero
`supabase.auth` calls — so everything is the `anon` role.

### Verification

`mlb_pipeline/verify_rls.py`. Baseline captured **before** applying:
76/76 relations readable, all 4 RPCs answering. After applying, `--verify`
checks read-neutrality per relation, RPCs still answer, writes are closed,
write-only tables still accept the write, and the must-deny set is denied.

What `prompt_templates` RLS does **not** fix: the app reads the prompt text to
render it on-device, so active templates must reach the client regardless of
policy. RLS cannot hide what the client renders. Closing that means moving
prompt rendering behind an edge function — an architecture change, not
something to slip into a security migration.

## RLS verification — my verifier was wrong, twice

Ran `--verify` after Andy applied both migrations. It reported 13 broken reads
and 6 "still writable" tables. **All of that was my measurement, not the
migration.**

1. **Reads.** I probed with `Prefer: count=exact`, which the app never sends.
   An exact count on 3.6M-row `line_history` hits the statement timeout and
   returns `57014` as a 500 — indistinguishable, in my output, from a policy
   breaking the read. Firing 76 of them back to back starved the rest.
   Re-probed in the app's own shape: **0 reads broken by RLS**, 72 normal, 4
   slow views (`v_prop_track_record`, `v_signal_records`,
   `v_signal_track_record`, `v_nfl_props_publishable`). Those are *views* —
   they have no RLS of their own — so it is performance, likely the
   CONCURRENTLY index builds plus the depleted IO budget.
2. **Writes.** Worse. A zero-row DELETE returns **200 with an empty array
   whether RLS denied it or it simply matched nothing**. The two are
   indistinguishable over REST, so every "PERMITTED" I printed was
   meaningless. Posture now comes from the catalog.

Also: the script printed `PASS: anon writes closed` on a run where it had
**skipped the write check entirely**. Fixed to exit INCONCLUSIVE — that false
all-clear is the exact failure mode the script exists to prevent.

### The hole 20261021c could never have closed

Part C only enabled RLS on tables that did not already have it, and Part A
only *adds* a SELECT policy. So tables already carrying an older policy were
left alone — and **21 of them have a policy named `"<thing> write anon"`
defined `FOR ALL USING (true) WITH CHECK (true)`**: the `ncaaf_*` and
`ncaab_*` context/results/stats/aliases tables, plus `daily_grades`,
`kenpom_cache`, `book_lines`, `mlb_player_game_log`, `outcomes`. `FOR ALL`
covers INSERT/UPDATE/DELETE, so enabling RLS changed nothing there.

Safe to drop, measured: **149 pipeline scripts use the service-role key;
exactly 1 uses the anon key, and it is the verifier I just added.** Nothing
writes as anon, and `service_role` carries BYPASSRLS.

`20261021d_rls_drop_anon_write_policies.sql` — drops them (restricted to
`cmd = 'ALL'` so no FOR SELECT policy is touched), plus a read-only
`get_rls_audit()` RPC so posture is read from `pg_policy` instead of guessed.
**Needs applying.** Local service key is `SUPABASE_KEY` in
`mlb_pipeline/.env` (JWT role claim confirmed `service_role`).

## NHL / NBA props — verified state, and why nothing publishes

Both tables are **100% COVERAGE tier, conviction 0.000 on every row**.

| | NHL | NBA |
|---|---|---|
| rows today | 420 (2 games) | 3,222 (12 games) |
| rows per (player, prop_type) | **1.00** | **1.58** (worst: 16) |
| `projection` populated | **column does not exist** | 371 / 3,222 (11.5%) |
| shadow rows in `prop_playbook_decisions` | **0** | 500 (capped) |
| publishable view | none | none |
| read by the app | game detail only | not at all |
| table total | **62,007 (largest in system)** | 7,367 |

### Four root causes, all verified

1. **The shadow is never promoted.** `prop_ensemble_scorer.py` runs in
   *shadow mode* — it writes only to `prop_playbook_decisions`. MLB has a
   second step that copies those scores onto the live rows. **NHL, NBA and
   NFL have no such step** (`markers=0` in all three workflows). So tier and
   conviction on the live rows stay COVERAGE/0 permanently, and the coverage
   gate then kills everything.
2. **The scorer is capped at 500 with no ORDER BY** —
   `prop_ensemble_scorer.py:999` is `'limit': limit or 500` and the workflows
   pass no `--limit`. NBA scores 500 of 3,222 props, and *which* 500 is
   arbitrary — the unordered-vintage trap again.
3. **No publishable surface.** `v_nhl_props_publishable` and
   `v_nba_props_publishable` do not exist in any migration (MLB has 19, NFL 8).
4. **NHL has no projection at all** — no projection column, and 0 shadow rows,
   so the scorer emits nothing for it. Consistent with the earlier finding
   that NHL prop inputs lose to the price.

NBA shadow output today: PASS 443 / **LEAN 56** / SKIP 1, conviction 50–73,
no STRONG and no PRIME. So even fully promoted, NBA yields leans, not anchors.

### Still open: `on_conflict` includes `prop_line`

Both generators upsert on
`game_date,player_name,prop_type,direction,prop_line`. When the line moves
between runs there is no conflict, so a **new row** is inserted — one per

## Prop signal calibration — every measurable NHL signal loses to its price

Worked the agreed order: calibration first, then the depth gate and the
duplicate signal.

### 1. Calibration

`mlb_pipeline/calibrate_prop_signals.py` re-evaluates each signal's own
`condition_expr` / `side_expr` against graded prop history. That matters
because the EXISTING calibrator (`refresh_prop_signal_calibration.py`, wired
daily for NHL and NBA since 09-08) depends on observed signal firings, and
NHL had none — no enrichment meant no decisions meant no firing records meant
no calibration meant blind weights. Circular. Re-evaluating expressions
retroactively breaks the loop.

What the existing one actually sees for NHL: **one "signal", `two_sided_price`
— a flag present on 100% of rows.** It calibrates market base rates and
tiers `sog_under 64.3% n=56` as VALIDATED, when ~64% simply *is* the price on
those props. Its tier bands are absolute (0.55/0.53/0.48) and price-blind.

Result, inside the publishable −300..+150 band:

| signal | hit | its own b/e | n | edge |
|---|---|---|---|---|
| `nhl_prop_l10_extreme` | 59.9% | 60.4% | 3,511 | −0.5 |
| `nhl_prop_l5_cold` | 59.9% | 60.0% | 2,331 | −0.0 |
| `nhl_player_l10_extreme` | 58.9% | 61.0% | 2,142 | −2.0 |
| `nhl_prop_season_hit_pct_high` | 47.1% | 53.5% | 1,919 | −6.4 |
| `nhl_prop_l5_hot` | 46.2% | 53.3% | 769 | −7.1 |

**Zero VALIDATED.** Three coin-flips whose CI spans breakeven, two losing in
both halves. 10 of 15 signals never fired on a graded row at all (inputs
don't exist).

Two corrections to my own measurement, both caught before reporting:

- **First pass averaged over every price in the table**, including a
  `points_under` at −650, and called all five ANTI_VALIDATED. **19,223 of
  25,478 firings (75%) are priced outside the band `apply_odds_band_gate`
  enforces** — three quarters of that measurement graded bets we'd SKIP.
- Rows whose lookback predates 10-03 lack the `before_date` guard and encode
  part of their own outcome, so they're excluded.

I also verified the FADE grading row by row before trusting any of it: an
`assists_over` with l10=2 fades to the under at −390 (79.6% bar), and the
over did lose. Grading a fade as if it rode with the row inverts it — the
same way 4 of 4 UFC fades were stored backwards.

### Why the flat bar is the core defect

`edge_weight` compares hit rate to `BREAKEVEN = 0.524`. Props run −300..+150,
where breakeven is 75% down to 40%. It points the wrong way in **both**
directions: against 52.4% the first three signals look like +6–7pp edges,
while `refresh_prop_signal_calibration` mislabels a base rate as VALIDATED.

`edge_weight` has always accepted a `baseline` argument and floors the bar at
`max(baseline, BREAKEVEN)` — its own comment notes no caller ever passed one.
`20261021e` adds `signal_registry.baseline_pct`; the prop scorer now passes
it. Current vs post-calibration weight:

| signal | registry now | weight | measured | weight after |
|---|---|---|---|---|
| `nhl_prop_l10_extreme` | 74.1% n=21,241 | **0.973** | 59.9 vs 60.4 | **0.0** |
| `nhl_prop_l5_cold` | 77.3% n=17,009 | **0.984** | 59.9 vs 60.0 | **0.0** |
| `nhl_player_l10_extreme` | 67.0% n=21,241 | **0.912** | 58.9 vs 61.0 | **0.0** |

Three near-maximum voices on numbers inflated by out-of-band props.

**The calibrator REFUSES to write when `baseline_pct` is absent.** Stripping
it isn't graceful — `edge_weight` would read 59.9% as a +7.5pp edge and take
a losing signal from the blind 0.20 to **0.71**. Worse than doing nothing.

### 2. Depth gate — a promotion rule outranked the evidence gate

`PROP_TIER_THRESHOLDS` asks 4 signals / 3 classes for PRIME and the gate
applying it is correct. Two legacy rules run *after* it and assign directly:

- **R3** `l10 >= 8` → COVERAGE→LEAN→STRONG→PRIME
- **R4** `l5 >= 4 and l10 >= 8` → PRIME when conviction ≥ 60

Neither consults min_signals/min_classes/min_score/min_margin, and both run
after the `conviction < 75 → STRONG` demote. A sampled NHL PRIME had score
0.409 (needs 0.60), margin 0.031 (needs 0.20), **1 signal** (needs 4), 1
class (needs 3), conviction 67 (needs 75). Failed everything, was PRIME.

**This was dormant and I activated it.** The rules key on
`player_l10_hit_count`, NULL everywhere because the conflict key orphaned the
enrichment. Fixing enrichment switched them on — PRIME went 0 → 64 in one run.

Fixed with one structural floor after all promotions rather than patching
each rule: a prop may not HOLD a tier whose bar it misses. Regression-checked
on real slates (today has no MLB/NFL card, so 0-scored would prove nothing):

| sport | floor demotions |
|---|---|
| MLB 10-19, 97 props | **0 — unchanged** |
| NFL 10-25, 173 props | **0 — unchanged** |
| NHL today | PRIME 64 + STRONG 4 → all LEAN |
| NBA today | 4; one PRIME→STRONG on score 0.571 vs 0.60 with 7 signals |

NBA is the sport with genuine depth (3–7 signals/row). NHL has one.

### 3. Duplicate signal

`*_player_l10_extreme` and `*_prop_l10_extreme` share condition, class and
strength. Only the side differs, and the former is **direction-blind** —
`BACK if l10>=8` regardless of over/under, so it backs the under on a player
who keeps clearing. Measured worse (−2.0 vs −0.5pp). Sharing a class also
bought two depth-gate entries for one piece of information.

`20261021f` disables it for NHL and NBA and replaces its stale 67% registry
claim with the measured in-band figure + baseline, sending its weight to 0.
`hit_rate` corrected rather than nulled, because NULL earns the 0.20
no-record prior instead of zero.

### NEEDS APPLYING — in order

1. **`20261021e`** — `signal_registry.baseline_pct`
2. **`20261021f`** — disable the direction-blind signal
3. then `python mlb_pipeline/calibrate_prop_signals.py --sport NHL --apply`

Until then the three 0.97-weight voices remain; the structural floor stops
them reaching PRIME but they still drive LEAN.

### 2. The 3-3 itself was a UTC/ET date bug — in EVERY surface, not just the Ledger

04:10 UTC), and whichever ran last owned the stored numbers.

d7_start became 10-16 instead of 10-15, so the seven-day window dropped its
earliest day:

| | stored | true |
|---|---|---|
| ledger d7 | 3-3 +1.10u | **4-4 +1.75u** |
| ledger d30 | 25-19 +12.64u | **26-20 +12.04u** |

Every surface shares `_windows_today`, so every d7 and d30 on the Receipts
tab was short a day whenever one of those runs went last. The worse case was
still ahead: `mtd_start = today.replace(day=1)` would have reset
month-to-date to near zero at 8pm ET on 10-31. Fixed with a zoneinfo ET date
(not a fixed −4, which breaks at the 11-01 DST change for the 04:10 run).
