## Prop line collapse — verified writing

NHL and NBA generators were storing one row per *posted* line, so five books
disagreeing on a number became five rows. Both now keep the line the most
books actually posted (not a median — a computed consensus of a 2.5/3.5 split
is 3.0, a line nobody posted, and a fake line makes a fake price).

Ran both for real: NHL 420 props upserted, NBA 1,874. Per-game collapse NBA
688 dropped → 168 kept (−80%), NHL ~145 → 115 (−53%). Every dropped row was
COVERAGE tier on a surface with no publishable view, so no product cost.

## 🚨🚨 RLS: the anon key can WRITE (incl. public_receipts)

The serious finding of the day, and it outranks the IO work.

RLS is disabled across the public schema. The anon key ships **inside the app
bundle** and can be read out of any installed copy. It is not limited to
reading — it can write. Verified from outside with the shipped key, using
DELETE and PATCH with a filter matching zero rows (nothing altered), getting
200/OK instead of 401/403 on:

| relation | why it matters |
|---|---|
| `public_receipts` | **the public graded record** — the whole "we show the receipts" brand |
| `prompt_templates` | the LLM prompts |
| `feature_flags` | what the app turns on |
| `sweat_tier_config` | the tier gates |
| `user_note_dispatch_log` | carries `user_id`, 1,070 rows |

Anyone able to UPDATE `public_receipts` can silently rewrite the record.

### Two measurement corrections, both mine

1. **First write probe was invalid.** I probed with a non-existent column and
   read 400 PGRST204 as "the privilege check passed." It does not: PGRST204
   comes from PostgREST's own schema cache, which rejects the payload before
   any SQL reaches Postgres. Re-ran with a zero-row DELETE/PATCH, which does
   reach the database.
2. **I over-called `user_notes`.** I described it as user data with 310 rows.
   It has no user columns at all — title/body/category/cohort/severity. It is
   broadcast notices the app is supposed to read. The real exposure is
   `user_note_dispatch_log` (`user_id`) and `prompt_templates`.

### Fix: `20261021c_rls_close_anon_writes.sql` — NOT YET APPLIED

Structured so it is read-neutral and write-closing, because there is no OTA
path and a broken read cannot be hot-fixed:

- **A** — every relation the client reaches via `.from()` (76), plus
  `ufc_picks`, which appears in **no** `.from()` call and is reachable only
  through `get_todays_ufc_picks()`. All four client RPCs carry no
  `SECURITY DEFINER` clause, so they run as SECURITY INVOKER with the
  caller's privileges; a table reached only through one still needs a read
  policy or that tab goes dark. RLS on + permissive SELECT → reads unchanged,
  writes denied (RLS default-denies any command with no matching policy).
- **B** — `user_note_dispatch_log` and `user_consent` are written by the
  client and never read back, so they get INSERT/UPDATE and **no** SELECT.
  Closes the `user_id` read exposure while keeping dismissals working.
- **C** — every other public table: RLS on, no policy = anon denied outright.
  `public_receipts` and `signal_attribution` land here. Safe because no
  migration anywhere sets `security_invoker`, so the `v_*` views run as owner
  and base-table RLS does not reach them — the view-backed tabs keep working.

Applied through a `DO` block checking `pg_class.relkind`, because 7 of the
listed relations are views and `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` on
a view is an error. Part C handles `insufficient_privilege` per table so one
extension-owned table (PostGIS `spatial_ref_sys`) cannot abort the block and
silently leave everything after it open.

The pipeline is unaffected: service-role bypasses RLS, and the one edge
function (`odds-proxy`) uses service role. No auth in the app at all — zero
`supabase.auth` calls — so everything is the `anon` role.

### Verification

`mlb_pipeline/verify_rls.py`. Baseline captured **before** applying:
76/76 relations readable, all 4 RPCs answering. After applying, `--verify`
checks read-neutrality per relation, RPCs still answer, writes are closed,
write-only tables still accept the write, and the must-deny set is denied.

What `prompt_templates` RLS does **not** fix: the app reads the prompt text to
render it on-device, so active templates must reach the client regardless of
policy. RLS cannot hide what the client renders. Closing that means moving
prompt rendering behind an edge function — an architecture change, not
something to slip into a security migration.

## Latent bug noticed, not fixed

`dismissNote` upserts `user_note_dispatch_log` with `onConflict:
'note_id,user_id'` but never sets `user_id`, and there is no auth, so
`user_id` is NULL. NULL never conflicts in a unique index, so every dismissal
inserts a new row — which is why there are 1,070 rows for ~310 notes. It is
wrapped in `try/catch` and labelled best-effort analytics, so nothing
user-facing breaks. Logged, not fixed.
