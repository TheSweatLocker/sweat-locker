## 2. 🚨 A one-day grading window makes every outage permanent

`grade_props.py` defaults to `--date yesterday_et()` with `--backfill 0`: **exactly one
date per run.** Both CI steps called it bare:

```
nba_pipeline.yml:  python grade_props.py --sport NBA
nhl_pipeline.yml:  python grade_props.py --sport NHL
```

A date the run misses is never revisited. And one was missed: `workflow_heartbeat`
has **no nba_pipeline or nhl_pipeline row between 2026-11-06 00:01Z and 2026-11-09
22:15Z** — a 3.9-day blackout. The grader came back on 11-09, graded "yesterday"
(11-08, which had no props), and 11-05's 348 props — two entire games — stayed NULL
permanently.

The deferral paths make it worse. Three places in `grade_prop` return `None`
*deliberately*, with the comment *"leaves result=null so the next grader run picks it
up once stats are real."* A one-day window cannot provide that next run. The three
10-26 props sat NULL for **20 days** for exactly this reason and resolved on the first
re-run I did.

**Fixed:** both steps now pass `--backfill 7`. To keep that nearly free, `grade_date`
now **counts the ungraded rows for a date before fetching that day's boxscores** —
previously it fetched a full day of player stats (for NBA, one scoreboard call plus one
summary call per game) before looking at whether a single prop needed grading, so a
7-day window would have paid that seven times per run to do nothing. An already-graded
date now costs one HEAD request. The count failing does **not** skip the date
(`feedback_zero_rows_is_a_wiring_error`) — it falls through to the full path and says so.

## 3. 🚨 The real bug: the boxscore key was normalised on one side only

`nba_data_client.get_player_boxscores` keys its map `displayName.lower()` — its
docstring says so. `grade_prop` looks it up with `_norm_name()`, which **also strips
periods, apostrophes and accents**:

```
props spelling 'Kelly Oubre Jr.'  -> _norm_name -> 'kelly oubre jr'
ESPN boxscore key                                 'kelly oubre jr.'
```

Every NBA player carrying one never matched. **And the miss was not a skip.** It fell
into `grade_date`'s "player not found in a FINAL boxscore" branch, which writes
`result='Void'` — a returned stake. Kelly Oubre played 23 minutes and took 3 rebounds
on 10-26 against a 3.5 line; both his props were Void.

Measured on the full table, row counts asserted against `count=exact`:

| population | n | Win | Loss | Void | **Void share** |
|---|---|---|---|---|---|
| name altered by `_norm_name` | 1,976 | 343 | 352 | 1,202 | **63.4%** |
| name unchanged | 31,342 | 13,543 | 14,026 | 2,429 | **8.1%** |

63.4% against 8.1%, and the names are exactly the predicted shape: Jabari Smith Jr,
Jaime Jaquez Jr, Wendell Carter Jr, Michael Porter Jr, De'Anthony Melton,
P.J. Washington, Ja'Kobe Walter, De'Aaron Fox.

Second, independent measurement against `nba_player_game_logs` (a different source
from ESPN): **1,791 Void props whose player has a unique log row with minutes > 0** —
they played. The repair's dry run then wanted to move **exactly 1,791** rows out of
Void. Two unrelated methods, same number.

**Why it never showed as a wrong record:** Void is excluded from every hit rate on
purpose. So this did not inflate or deflate anything — it silently *removed* ~1.8k real
outcomes from every NBA measurement.

**The NHL path has been right since 09-23** because it builds its keys with
`_norm_name` from the prop names themselves. The NBA path returned the client's dict
verbatim and never got the same treatment.

**Fixed** in `fetch_nba_player_stats_for_date`: fold the keys with `_norm_name`, and
where two ESPN spellings collide onto one key, store a present-but-statless marker so
the row is left **ungraded** — never guessed, and never Voided either. Folded at the
lookup, not in `nba_data_client`, whose contract is "ESPN's spelling, lowercased" and
which other callers rely on. Zero collisions across all 22 dates.

## 6. 🚨 Third instance, found by checking my own fix: `limit=5000` returns 1,000

Grading NHL 11-14 cleared the NULLs but produced **426 Void of 1,414 — 30%**, with
*"411 props skipped — player not found in boxscore"*. That is the exact shape of §3, so
I checked rather than accepting it.

`fetch_nhl_player_stats_for_date` derives its player set from the props for that date:

```python
params={'select': 'player_name', 'game_date': f'eq.{date_str}', 'limit': '5000'}
```

Proven by hand against the live API:

```
asked limit=5000 -> 1000 rows   content-range: 0-999/1414
```

PostgREST caps the response server-side. Asking above the cap does not raise — **it
silently truncates**, and the read is unordered, so a different subset each run. Every
player appearing only in the rows past the cap was absent from `stats_map`, which sends
the prop into the same "player not found in a FINAL boxscore" branch, which writes
`Void`. **411 of 1,414 NHL props were booked as returned stakes on games the players
played.**

**Fixed:** paginate with `count=exact` and **refuse to grade from a partial player
set** — a short read here does not under-report, it invents no-actions. Re-run:

```
before:  295 names (from 1,000 of 1,414 rows)  ->  231 stat rows
         graded 514W 474L 426Void   n=  988   52.0%
after :  327 names (from 1,414 of 1,414 rows)  ->  326 stat rows
         graded 732W 664L  18Void   n=1,396   52.4%
```

**Void 426 -> 18, and 408 real outcomes recovered.** The hit rate barely moved
(52.0% -> 52.4%), so the voiding was close to side-neutral on this date — it was
destroying sample, not bending the record. The single remaining skip is the one
player who does not resolve to an nhle.com id, correctly left rather than guessed.

The 231-vs-295 gap was `_norm_name` folding accented duplicates, not failed resolution —
confirmed because the "did not resolve" warning fires for exactly 1 player only now that
the set is complete.

**And this is endemic.** `limit` above 1,000 has been fixed by hand at least six times in
this repo (09-12, 09-13 across `dedup_prop_dupes`, `generate_daily_degen`,
`grade_prop_playbook`, `generate_sweat_card`, `detect_line_movement`,
`audit_projection_accuracy`, each with its own comment saying so). **41 such reads are
still live across 34 files** — `mlb_postseason_prop_gate.py` (3),
`nfl_prop_injury_filter.py` (2), `generate_sweat_card.py` (2), and 31 more with one each.
Not audited: whether each one's filtered set actually exceeds 1,000 needs checking per

## 1. 🚨 A POTD was settled Void while its game was still 2.5 hours from kickoff

`daily_best_bet_history.id=1215` — the **2026-11-14 POTD**, Ole Miss ML +120, Jerry 79 —
read `result='Void'`, `resolved_at=NULL`. ESPN:

```
Ole Miss Rebels at Oklahoma Sooners  2026-11-15T18:00Z  STATUS_SCHEDULED
                                     Sun, November 15th at 1:00 PM EST
```

The game had not been played. Void is a returned stake and every record surface excludes
it by design, so the most visible pick of the day was deleted from the record rather than
graded — and today's card recap still showed it as "Pending", so the two surfaces
disagreed as well.

**Cause.** `ncaaf_game_results` holds **two** rows for this matchup:

```
ncaaf_20261114_Ole Miss_Oklahoma   2026-11-14   None-None   <- phantom
ncaaf_20261115_Ole Miss_Oklahoma   2026-11-15   None-None   <- the real game
```

`void_orphaned_picks.build_rescheduled()` treats "an unplayed past row with the same
teams listed later" as proof of a re-date, and re-dated games **bypass the 4-day
timeout** and void immediately. That logic was written for TB @ CLE on 10-16, where the
earlier row really was the postponed game. Here the *earlier* row is the phantom, so the
real upcoming game played the part of the successor, and the pick was settled on day one
— the exact outcome the function's own docstring forbids: *"voiding early would destroy
a live pick."*

The phantom pattern is not isolated. Same morning, same tables:

```
ncaab  Washington @ Utah       11-14, 11-15, 12-05   (ESPN: real game is 12-05)
ncaab  Idaho St. @ Seattle     11-14, 11-15, 11-17   (ESPN: real game is 11-15)
ncaab  Air Force @ Pacific     11-14, 11-15          (ESPN: genuine POSTPONED → 11-15)
ncaaf  Ole Miss  @ Oklahoma    11-14, 11-15          (ESPN: real game is 11-15)
```

Only Air Force @ Pacific is a real postponement. No picks ride the NCAAB phantoms today
(33 NCAAB reads checked, none on those game_ids), so the POTD was the only casualty.

**Fixed, two places.**

1. `void_orphaned_picks.py` — the re-date conclusion now demands of the successor what
   makes it a successor: that it has **actually come and gone** (a score, or a date
   already past). A row dated today or in the future is a game that has not been played,
   so nothing has been missed and the pick is live, not orphaned. Re-dated set 34 → 30;
   every genuine historical MLB postponement is retained, and the four live entries now
   print `NOT a re-date yet, pick left live`. Air Force @ Pacific gets voided one day
   later than before — the price of not settling a live pick.

2. `grade_potd.py` — closing the gap that made Void look like the only way to resolve
   these. `game_id` is date-stamped in every sport, so a moved game mints a new id and
   the pick's own id points at a row that will never carry a score. `_fetch_game_result`
   now follows the matchup forward to the row that **has** one, bounded to +5 days so a
   pick can never be graded against the next meeting of the same teams weeks later.
   Verified on three cases:

   ```
   MLB 2026-07-21 BAL @ BOS   -> re-dated: grading against the 2026-07-22 result (5-1)
   NCAAF 2026-11-14 Ole Miss  -> None   (successor unplayed — correct, grades tonight)
   NCAAB 2026-11-14 Wash@Utah -> None   (12-05 is beyond the window — correctly refused)
   ```
