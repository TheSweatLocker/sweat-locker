### How it was done, and what was deliberately NOT done
* The card blob was edited in place. `sharp_card_2026-10-08` is HARD-LOCKED
  (past the 12:00 ET lock, card has real content), so no cron and not even
  `--force` can revert it — only `SHARP_CARD_EMERGENCY_UNLOCK=1`. The edit is
  durable for the day. Guarded: the script refuses unless `items[0]` is still
  the expected Cleveland/stale entry.
* **Receipt identity was not rewritten.** The `20260918b` trigger silently
  reverts `pick_label` / `pick_side` / `tier` / `conviction` / `pick_odds` to
  OLD on UPDATE — a PATCH returns 200 and changes nothing. That freeze is
  correct: you must not be able to quietly change which side a published
  receipt backed. So receipt **1249643** was marked `NO_ACTION` (result IS
  mutable) and a new receipt **1301862** was inserted. Both rows survive, so
  the pull is visible rather than erased, and the Ledger counts only the
  Chicago side.
* Two insert attempts failed first and are worth remembering: `source_table`
  and `source_id` are NOT NULL (23502), and
  `public_receipts_capture_mode_chk` allows only `('live','reconstructed')`
  (23514) — `manual_override` is rejected, so `capture_mode='live'` with the
  override recorded in `audit`.

### Trust note
This is the exact thing the hard lock exists to prevent — a published Sharp
pick changing mid-day, from Andy's own directive *"whatever comes out in the
morning stays."* Anyone who saw the morning board sees a different MLB pick
now. Taken knowingly: the morning pick was a stale-row artifact rather than
re-scoring churn, the game had not started, and Andy made the call. If this
needs to be repeatable, the right build is a proper override path with its own
receipt lineage — not a hand-run script.
