## EVENING II · "NBA and NFL pipeline failed" — and why the database could not say so

### The gate's own telemetry has never recorded a single row

`workflow_heartbeat` since 2026-11-04: `step_failed` **16 rows**, `step_failures`
**0**, `step_durations` **0**. The per-step failures land; the gate's two
summaries never have.

Both gate payloads are built by embedded Python containing a **literal newline
inside a single-quoted string**:

```python
part = line.rstrip('
').split('	', 1)                 # PYDUR  — step_durations
lines = [l.rstrip('
') for l in open(sys.argv[1], ...)]   # PYJSON — step_failures
```

Each is a `SyntaxError: unterminated string literal`, and each is invoked as
`python3 - ... 2>/dev/null || true`, so the error is discarded, the JSON file is
empty, `[ -s ... ]` is false and no POST happens. Silent by construction.

Verified by extracting all four heredocs and parsing them: `PYHB` and `PYSK`
(the per-step ones, which work) parse; `PYDUR` and `PYJSON` do not. Fixed, and
all four parse now; the payloads build correctly including a label with embedded
double quotes, which the file's own comment says a hand-rolled escape had once
broken.

This matters beyond tidiness. `step_durations` was added on 2026-11-02
specifically because the 11-01 `daily_card` runs were killed by the job timeout
and "nothing could say WHICH step ate the clock." It has never answered that
question, because it has never run.

**A note on how this was fixed.** Two earlier replacement attempts printed
"patched" and changed nothing — the escape collapsed so `old == new` and
`str.replace` was a no-op on a string it matched exactly once. `git diff` was
what caught it. The third attempt builds the bytes from explicit values and
asserts `old != new` before writing, then reads back and counts both forms.
A no-op replacement reports success; only a readback distinguishes it.

- fetch raised
- ESPN returned non-200
- 0 rows parsed (layout change)
- rows parsed, none persisted

`run_step.sh` captures **stderr only**, deliberately — its own note explains that
piping stdout flips Python to block buffering and merges the streams across ~100
steps. That is right for a traceback, which goes to stderr by itself, and wrong
for a script that catches its own errors and reports them in prose. The one line
naming which mode fired was the one line never collected.

human reading the log, stderr so the reason lands in `workflow_heartbeat`.
Verified: the script still runs clean locally (94/94 rows persisted, rc=0) and a
simulated failure now appears on stderr.
