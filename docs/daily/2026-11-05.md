### The gate's own telemetry has never recorded a single row

Both gate payloads are built by embedded Python containing a **literal newline


Each is a `SyntaxError: unterminated string literal`, and each is invoked as

double quotes, which the file's own comment says a hand-rolled escape had once
broken.

## EVENING IV · Why I couldn't verify NCAAB, and the 1000-row cap behind it

Andy: "why cant you verify? ... Not verifying NCAAB against market is
unacceptable."

Correct on both counts. "Unjoinable" was giving up on a problem the repo had
already solved, and the deeper reason was a one-character-class bug that had
capped the whole module.

### `side` contains the substring "id"

`market_line._page` is a keyset paginator. It decides whether to add the cursor
column to the select like this:

```python
want_id = 'id' not in str(params.get('select', ''))
```

A **substring** test for a column **name**. Every caller selects
`matchup,side,book,line,price,captured_at,commence_time` — and `side` contains
`id`. So the test concluded `id` was already selected, never added it,
`chunk[-1]['id']` raised `KeyError`, and the `except (KeyError, TypeError)`
directly below returned after exactly **one page**.

Measured before the fix — three sports, one number, which is the signature:

| | before | after |
|---|---|---|
| NFL spread quotes | **1000** | 120,000 (cap) |
| NCAAB | **1000** | 22,496 |
| NHL | **1000** | 22,968 |
| NBA | **1000** | 43,140 |

**111 files import `market_line`.** It is the repo's answer to "what did the
books actually post", and every consumer has been reading the first 1000 rows
of `line_history`. The clearest casualty is `audit_published_lines.py` — the
detector built to answer exactly Andy's question — which printed
`no data 100.0%` on every pick. That reads like a clean run, not like a
detector that cannot see.

Fixed by comparing **tokens**, not substrings, and treating `*` as already
carrying id.

### NCAAB never joined because the resolver was never wired in

`market_line.build_matcher` matched non-NFL sports by prefix:
`h.startswith(nh)`. That cannot join NCAAB — context holds canonical short
names (`Penn`, `Penn St.`, `Quinnipiac`), `line_history` holds the Odds API
spelling (`Pennsylvania Quakers`, `Penn State Nittany Lions`). Worse, `Penn`
**is** a prefix of `Penn State`, which is the wrong-fixture hazard the function
exists to refuse.

`ncaab_team_resolver` already solves this against `ncaab_team_aliases` and its
own docstring reports 75 of 78 games joined. It is now wired into the matcher,
with both halves resolved through the same table and compared **whole**, never
by prefix.

## OVERNIGHT II · The receipt guard was hiding its own findings, and NCAAB results are a day late

### 🚨 An early WARN was short-circuiting a later REFUSE

`receipt_invariants.check_row` returned on the first rule that fired,
**including the rules that only WARN**. So a row that was both priceless and
carrying a fabricated line returned `('WARN', 'no pick_odds')` from rule (1)
and never reached rule (1b) at all — and priceless is exactly the population
that has fabricated lines.

Measured: the new label check matched **14** rows when tested directly but only
**2** through `check_row`. The other 12 were short-circuited.

A WARN is now remembered and the rules keep running; the most severe finding
wins. Replayed over all **42,405** receipts since 09-01: **exactly 25 rows move
WARN → REFUSE and none move the other way.** All 25 are fabricated lines the
WARN was hiding. 0.06% of the table, so it refuses the defect and essentially
nothing else.

### The fake number can hide in the label

Rule (1b) keyed on `pick_line`, so a projection written into `pick_label` while
`pick_line` stayed NULL walked straight past it —
`_void_fabricated_line_receipts_1102.py` used the same key and could not see
them either. 14 rows: `Under 155.7`, `Under 154.75`, `Under 155.3` — the same
NCAAB projected totals, stored one field over.

Rule 1b now reads the label when the line is NULL, anchored on the
over/under word so a team name with digits cannot match.

**Cleared 23 ungraded rows** (33 were already VOID, and **1 is left alone**:
id 9296, `Over 8.7`, 2026-09-18, already settled as a **WIN** on a line no book
posted — a wrong grade is part of the published record and needs its own repair
path, not a quiet void).

**97 ML receipts past the −300 juice cap**, at prices including **−100000,

### 🚨 NCAAB results are filed a day late, and that is the grading debt

All 34 ungraded NCAAB game_ids ARE in `ncaab_game_context`, and **none** of
them matched a result row — while 225 result rows exist in the window.

`resolve_ncaab_results.event_to_outcome`:

```python
dt = datetime.fromisoformat(commence.replace('Z', '+00:00'))
game_date = dt.date().isoformat()
game_id = f'ncaab_{dt.strftime("%Y%m%d")}_{away_team}_{home_team}'
```

Both the `game_date` **and** the composed `game_id` come from ESPN's **raw UTC
timestamp**, with no ET conversion. A 7pm ET tip is 00:00 UTC the next day, and
for NCAAB that is most of the slate.

| date | games in context | rows in results |
|---|---|---|
| 2026-11-02 | **119** | 30 |
| 2026-11-03 | 19 | **144** |
| 2026-11-04 | 10 | 25 |
| 2026-11-06 | 42 | 33 ← tonight's late games, already filed as tomorrow |

11-02's ~89 evening games are sitting under 11-03. A receipt on a 11-02 game
can never find its result row, because the result is stored under 11-03.

This is the same bug class `nfl_game_context` already documents and fixed —
"NFL's marquee windows all cross UTC midnight … so those games were filed one
day late, onto dates with no NFL games at all" — and `sweat_dates.et_today()`
exists for it.

Running the resolver confirms the consequence: `--date 20261102` pulls **182
ESPN events, 165 finals**, and matches **0 of 165** existing rows, because it
composes ids a day ahead of the 30 already stored. `--date 20261104` emitted
`ncaab_20261105_*` ids.

**NOT deployed, deliberately.** The date is embedded in `game_id`, so changing
the derivation mid-stream makes the resolver INSERT fresh rows beside the
misdated ones instead of patching them — 165 duplicates on one date, in the
table that grades the record. The fix needs to be migration-aware: convert to
ET for both fields, and have the existing-row lookup try the legacy UTC-dated
id as well so historical rows get PATCHED rather than duplicated. That is a
change to the published record and it should be made awake, with the dedupe
tested. Filed as **R166**, top of the list.
