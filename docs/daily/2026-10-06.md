`audit_prop_grades.py` (`e35a7bad`) checks every published grade against
`mlb_player_game_log` / `nfl_player_stats` — tables the settler never reads,
so the verdict is independent of the code under audit.


## Tiering: what is actually wrong

The ladder **works** — hit rate declines monotonically across 744 clean picks
(PRIME 59.4% → STRONG 54.4% → LEAN 50.4%). It is not inverted.

What fails is price:

| tier | hit | market implies | edge | ROI | median odds |
|---|---|---|---|---|---|
| PRIME | 59.2% | **61.3%** | **−2.1pp** | −4.8% | −145 |
| STRONG | 54.4% | 55.2% | −0.8pp | −1.5% | −119 |
| LEAN | 50.4% | 54.9% | −4.5pp | −8.2% | −118 |
| COVERAGE | 60.4% | **49.0%** | **+11.3pp** | **+24.0%** | **+110** |

Same signature on sides+totals (PRIME 57.8% vs 57.9% implied). **Not a prop
problem — a tiering problem.** 26.4% of PRIME props sit at −200 or worse,
where the −250+ bucket returns 69.9% hit for −12.9% ROI.

**But the premise is only half-supported**, because of what price capture
turned out to be doing — see below. Three hypotheses were tested and failed:
edge-ranking (`conviction − implied` as a filter returns −6.3% vs −0.7% for
its complement; conviction is not a probability so the proxy is noise),
price-alone (no monotonic pattern), tier-within-price (cells of 30–50, noise).

`refit_conviction` does not help: **3.8% board coverage** (386 of 10,202 since
09-22), 100% on er/ks families and **0% on every high-volume batter family**,
flat ladder, and it is another *probability* estimate so it would rank the
same overpriced picks first. It lands in a different tier band than base
conviction **59.3% of the time** (median gap 18.3, max 69.6) — which is the
whole reason a PRIME can display a conviction of 24.

## The finding that reframes it: we publish worse than the price we saw

Of 408 reads carrying both a taken price and a best-available price:

```
pick price == best available     28  ( 7%)
pick price WORSE than best      380  (93%)
median give-up when worse       1.11pp of implied probability
```

PRIME's deficit is −2.1pp. We give up a median 1.11pp at the point of
recording. **Plausibly about half the shortfall is self-inflicted**, which is
a different fix from "pick better props".

Verified `pick_odds` is the **publish** price, not the close: 318 of 326
game_read receipts match `price_american`, **zero** match
`close_price_american`. Also: `close_price_american` is empty on **every**
read, so CLV and line movement are currently unmeasurable, and only 418 of
1,641 reads carry any price at all.

**So price capture comes before any tiering change.** Tuning selection against
a number that is partly a bookkeeping artifact would bake the artifact in.

## The Fade — built, then rebuilt on the right column (`462de172`)

Andy approved the fade-the-public ATS tracker for all sports. First version
published, then audited before trusting it — and the audit retracted most of
the numbers I had just given him.

**Three defects, all upstream of the arithmetic:**

1. **Three of four sources measured the wrong side.** `archive_public_splits.py`
   keys each source differently:

   | reader | archive key | what `pick_side` holds |
   |---|---|---|
   | `latest_oc` | `(game_id, market, pick_side)` | the actual side |
   | `latest_fr` | `(game_id, market, sharp_side_norm)` | the **sharp** side |
   | `latest_ftp` | `(game_id, market, sharp_side_norm)` | the **sharp** side |
   | `latest_cz` | `(game_id, market, sharp_side_norm)` | the **sharp** side |

   So for fr/ftp/cz a ≥65% reading is *"sharp and public agree"* — consensus,
   the opposite of a fade. Their means confirm it: fr 41.2, ftp 43.2 (a sharp
   side normally holds a **minority** of tickets) against oc 63.6.

   `cz` is not a share at all. It reads `cleatz_signals.sharp_bets_pct`, which
   lands on exactly 100.0 in **4,297 of 28,211 rows (15.2%)** and on 0 never,
   while fr/ftp/oc hit 100% **zero times across 139,188 values**. Averaging
   produced readings like Liberty 71.3% out of cz 100.0 + fr 57.0 + ftp 57.0 —
   a sharp-side number dragging a public-side number over the line. Same shape
   as `returning_rush_yards` holding `totalRushingPPA`.

2. **Dedup-then-read was discarding real readings.** Both paths took the latest
   capture per (game, side) and *then* read the column. The four scrapers run
   independently, so the newest row for a game often has `oc=NULL` because that
   pull only reached fr/cz — throwing away an oc value one capture earlier.
   Worked example: Dodgers @ Braves 10-06, oc had the Dodgers at 75.0% of
   tickets, newest row `oc=NULL`, game vanished from both the record and the
   live list. `latest_readings()` now takes the latest **non-null** reading per
   source. Recovered 36 NCAAF games and flipped that sign, −9.1% → +3.8%.

3. **A sport with no qualifying games kept its row.** The first run published
   NHL 5-9 / −31.82% off sharp-side columns. On the corrected source NHL has
   n=0, and the upsert left that number in the app behind a stale
   `last_computed_at`. The writer now reconciles both directions.

# 2026-10-07 — WORKING THE LIST TOP-DOWN

Andy: "every day it's 'here's what is uncovered' ... will this continue, how do

## WHY IT WAS FLIPPING

`jerry_reads_dual_write` upserts on `sport,game_id,game_date`, so every
regeneration rewrote `call_market/call_side/call_line` on the **same row id**,
and `public_receipts` cites that id. Every read regeneration was a chance to
change what an already-published pick pointed at.

Measured across all 1,340 receipts citing jerry_reads:

| | count | share |
|---|---|---|
| agrees with its cited read | 1,091 | 81.4% |
| market differs | 186 | |
| side and/or line differs | 63 | |
| cited row gone | 2 | |
| **disagree** | **249** | **18.6%** |

Receipt "Alabama −11.5" cites a read calling South Carolina +12.5. "BUF ML"
cites one calling Over 50.5.

## THE THREE PATHS, ALL CLOSED

| path | fix |
|---|---|
| props **deleted** under a receipt | prune demotes to SKIP · `1a75aad7` |
| reads **rewritten** under a receipt | call frozen once published · `cde89fc3` |
| receipts themselves | already immutable in Postgres |

## HOW WE KNOW WHAT'S RIGHT

The receipt, and it is enforced in the database, not in Python.
`20260918b_receipt_enrichment_allow` + `trg_freeze_receipt_identity`:

* **fully frozen** — sport, surface, market, game_date, published_at,
  player_name, prop_type, **pick_side, pick_line, pick_label**, source_table,
  source_id
* **set-once** (NULL→value only) — tier, conviction, pick_odds, matchup, audit
* **mutable** — result, actual_value, graded_at

And `grade_public_receipts` resolves from the receipt's own `pick_label`, never
from the source row. So what we told users and whether it won cannot be
rewritten. What drifted was the lineage *pointer*, never the record.
