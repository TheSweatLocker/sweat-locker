## Reads are clean across all four sports

Closed the last prose defects. Every live read now carries real prose, no
stubs, no parser markers, no engine jargon:

        sport  reads  dupes  stubs  no long  jargon  no price
        MLB       12      0      0        0       0         0
        NFL       18      0      0        0       0         0
        NCAAF     85      0      0        0       0         4
        NHL       37      0      0        0       0        29

152 live reads. The 29 unpriced NHL are preseason — no book quotes exist
yet, so a price would have to be invented. The 4 NCAAF are the same
shape.

Two fixes got it there (`13a331c9`):

- **Marker leak.** Three NFL reads had `short_read` literally beginning
  `---SHORT---`. A section marker is a parser instruction and must never
  reach a subscriber. `parse_synthesis` was not at fault — running it on
  the stored strings returns clean prose — so some write path handed over
  the raw narrative instead of the parsed sections. Rather than hunt every
  caller that might, `upsert_jerry_read` now re-parses whenever a marker
  is present; it is the last gate before the write, so it catches bad text
  regardless of origin. Repaired all three in place, no LLM call needed.
- **NHL horizon.** The generator copied NCAAB's "today + 5 days" and
  instantly left three games stubbed — `nhl_game_context` reaches 09-30
  while the generator stopped at 09-29, so the edge of the window kept the
  exact placeholder the generator exists to replace. A second horizon that
  disagrees with the context table's own reach can only ever do that. It
  now reads whatever context holds. 34 → 37 of 37.

## The NFL prop projection: fixed, measured, and it does not pay

I have been calling this the only measured win on the board and quoting
**58.3% against a 50.8% live rate, all session. That was wrong. I am
retracting it.**

**The bug was real** (`2606fedf`). Every NFL prop pick is justified by a
projection — the `0.60*L4 + 0.35*season + 0.05*baseline` blend, or the
fantasy-weighted variant. `nfl_generate_props` computes it, stores it in
the row dict, prints it in dry-run, and then threw it away on every real
write. `projection` was NULL on **1,794 of 1,796 rows**.

It was invisible because `_to_pipeline_props_shape` — the bridge to the
canonical table — simply never listed the field. A mapper that omits a key
returns a valid dict, so PostgREST answered 200 and every run reported
success. Its docstring made it worse by claiming the bridge was
"dual-write" and `nfl_props` was still read; untrue since 2026-09-03, when
`nfl_props` was found dead and this bridge became the only write path.
Anyone checking would conclude the field landed elsewhere. It landed
nowhere.

Three enabled signals gate on it and were dead since 2026-08-22 —
including the FADE guard meant to refuse a prop whose own projection
contradicts its direction. A NULL makes `condition_expr` evaluate False
rather than raise, so even the eval-error logger added in the 8/22 audit
stayed quiet. **Same bug NBA had and had "fixed"; NFL was never checked.**

**Fixed at the mapper, not with a guard.** Patching one field would only
wait for the next, so every key the generator emits is now accounted for:
mapped, or listed in `_BRIDGE_INTENTIONALLY_DROPPED` with the reason. An
unaccounted key raises on the first row. Verified both directions.

History repaired without re-scraping. `signals.edge_pct` is the
directional edge the generator computed, so the projection inverts exactly
out of the stored arithmetic. Corroborated by recomputing the blend from
the stored inputs, which shares no arithmetic with the inversion: 602 rows
match the plain blend, 968 more match once the fantasy lens is included —
1,570 of 1,792 confirmed twice. 1,792/1,792 patched, 0 failed. Only
`projection` was touched, so no line, odds, tier or grade moved.

**Then the measurement said don't bet on it.** 1,331 graded props:

        all                     677-654   50.9%
        edge <15% (no signal)   263-269   49.4%
        edge >=15% (supports)   414-385   51.8%
        edge >=30% (strong)     214-199   51.8%

Breakeven at -110 is 52.4%. The best bucket is 0.6pp *under* it. And
there is no monotonicity — 6-10% 46.5%, 10-15% 52.6%, 15-20% 55.5%,
20-30% 49.4%, 30-40% 49.3%, 40%+ 53.0%. A 30%+ edge performs identically
to a 15%+ edge, which is precisely what
`nfl_prop_projection_strong` asserts at weight 0.75.

I tried to reproduce 58.3% under the most charitable reading — that I had
measured the projection's raw directional skill rather than graded pick
results. Same number, 677/1331, because the generator already refuses
wrong-side picks so the published side always equals the projection's
side. No framing of this data yields 58.3%.

**Nothing hand-tuned in response.** `backfill_prop_signal_tiers.py`
already turns graded outcomes into registry weights and could never run on
these signals while `projection` was NULL. Run for NFL it reproduces the
numbers independently (799 fires 414-385; 413 fires 214-199) and
`edge_weight` zeroes them on evidence:

        nfl_prop_projection_edge_supports  51.8%  n=799  ->  0.000
        nfl_prop_projection_strong         51.8%  n=413  ->  0.000
        nfl_prop_l5_hot_streak             51.6%  n=409  ->  0.000
        nfl_prop_l10_extreme_extreme       44.3%  n=221  ->  0.000  ANTI
        nfl_prop_season_hit_pct_high       36.9%  n=149  ->  0.000  ANTI
        nfl_prop_l5_cold_streak            54.7%  n=117  ->  0.318

Right outcome in both directions: persisting the projection was a
correctness bug worth fixing regardless, and the moment it was persisted
the evidence said do not weight it. Populating it *without* calibrating
would have armed three unearned signals at the 0.15 blind prior on ship
day.

## NBA: the 8/22 fix broke the write it was fixing

Found while checking whether the NFL bug had spread (`dc91475f`). It had
not — MLB stores its projection as prose inside `signals`, a genuinely
different data model, and NFL was the only sport with the numeric column.
NBA was broken the other way.

`nba_pipeline_props` has `projected_value`. It does **not** have
`projection`. Three enabled signals read the name that was never created.
The 8/22 audit noticed them returning None and made
`enrich_nba_prop_projections.py` write both keys — except the new key
names no column, and PostgREST rejects the whole statement on an unknown
column. So the patch stopped writing anything at all, including the
`projected_value` half that had worked. Verified against a non-matching
id, so nothing was written to find out:

        {projection, projected_value} -> 400 PGRST204
        {projected_value}             -> 204

The fix converted three dead signals into three dead signals plus a dead
write. It has never once succeeded. Invisible only because the table is
empty (NBA props on hold) — it would have surfaced on **opening night,
10-21**, as props shipping with three absent signals.

`20260924b_nba_prop_projection_column.sql` adds the column, named to match
NFL's so the signal expressions stay portable. **NOT YET APPLIED.**

The script also had no failure branch — successes counted, failures not,
so a 100% outage printed a bare "patched 0" with no reason. It now prints
the status and body per distinct failure.

## Second pass: the calibration framework itself was broken

### Both scorers read only the first 1000 registry rows (`1c6d9129`)

`signal_registry` holds 1,195 rows. Both scorers fetched it with a bare
GET, so they got 1,000 and **195 calibrations were simply absent**.
PostgREST reports the cap in a header nobody read, and a missing registry
row falls back to the no-record prior instead of erroring — so it never
surfaced. It silently repriced live signals:

        ncaaf_fbs_vs_fcs_early_season  63.8% n=69   VALIDATED  0.783 -> 0.150
        mc_strong_away_ml              58.5% n=53   VALIDATED  0.552 -> 0.150
        ncaaf_ol_weight_adv_home       56.3% n=135  VALIDATED  0.478 -> 0.150
        home_pitcher_owns_opp          46.2% n=26   ANTI       0.000 -> 0.150
        confluence_home_lean           50.5% n=105  UNVALID    0.000 -> 0.150

Both directions at once: proven signals ran at a fifth of their earned
weight, and signals measured to be actively wrong got **un-muted** from
0.000 to the blind prior. 36 enabled signals affected across MLB, NFL and
NCAAF — in the loader that sets every conviction in the product.

One paginated fetch now lives in `ensemble_scorer` and the prop scorer
imports it, rather than the repo gaining a seventh copy of `_paginate`.

Also fixed the **scope collision**: `_load_registry`'s own docstring
records fixing this exact "last-loaded wins" bug one dimension up (sport,
2026-08-21). It remained at `market_scope`, which is part of the table's
real unique key. `long_rest_home_ats` MLB is 57.0% VALIDATED on `spread`
and 48.1% UNVALIDATED on `rl` — a 0.5-vs-0.0 weight decided by row order.
Now deterministic (larger graded sample wins) and counted in the log.

Blast radius checked and **not user-facing**: the prop playbook now
declines all 381 NFL props for 09-27 where it used to write decisions, but
that layer is shadow — `write_decision` only inserts into
`prop_playbook_decisions`, and `v_nfl_props_publishable` reads
`nfl_pipeline_props` joined to prop jerry with no reference to it. Verified
live: 51 NFL and 4 MLB props still publishable. It is real input to the
playbook cutover decision though — on measured weights the playbook ships
zero NFL props, the same verdict as the 50.9% hit rate.

### `league_baseline` was calibrated as a proven money loser (`1bb93fed`, `6ed84533`)

`signal_contribution_tracker` counted **every key in the signals blob** as
a signal. That blob holds fired signals AND the model inputs recorded for
the audit trail, so eight NFL input fields were measured, tiered, and
written to `signal_registry`:

        l4  label  opp_col  opp_pct  edge_pct  games_used
        season_avg  league_baseline

All identical, because all eight are present on every graded prop — their
"hit rate" is the base rate. `league_baseline` is a per-stat constant.
`label` is a display string ("Receptions"). None can win or lose a bet,
and all were labelled ANTI_VALIDATED proven money losers.

The test is deliberately **not** a denylist or a type check — a fired
signal can be bool (`fade_jerry_pass`) or str (`weather_calm`), exactly
like the metadata. What separates them is information content: a key
present on every graded row has `hit_rate(fired)` arithmetically equal to
`hit_rate(population)`, so it cannot be evidence about anything. Real
signals fire on a subset (760, 606, 490 … 45 of 1,803). The tracker now
drops those and **reports them**, so a new input field shows up instead of
quietly becoming a calibrated signal.

Targeted, not destructive: NFL drops exactly those 8 and keeps 18 real
signals; **MLB drops nothing** — 0 universal keys over 26,846 graded props.

First purge pass only looked at `market_scope in ('prop','*')` and found 8.
The calibrator also writes one row per prop family, so the same 8 names
existed **112 more times** under scopes like `reception_yds_over` — `label`
tiered DISCOVERY at 53.9% on receptions overs. Scope was never part of the
question. **120 fake rows deleted**, registry 1,195 → 1,075 — still above
the 1000 cap, so the pagination fix is still doing real work. Collisions
fell 255 → 143 as a side effect.

Also: `refresh_prop_signal_calibration`'s docstring still advertised the
pre-09-02 tier bands while `_tier_for` implements the tightened ones, so a
51.4% ANTI_VALIDATED row reads as a bug against the docs and is correct
against the code. Second stale-docstring-as-defect today.

### NFL prop tiers rank backwards (`6f392bf1`)

        PRIME     32-25    56.1%  n=57    above -110
        STRONG   170-164   50.9%  n=334   BELOW -110
        LIGHT    140-159   46.8%  n=299   BELOW -110

LEAN is the lowest published tier and the best performer. STRONG and LIGHT

**Verified clean, not assumed clean.** All 1,331 graded NFL props predate
the 09-22 leak fix, so the first question was whether this is another leak
artifact. The leak was MLB-specific (`fetch_mlb_player_recent`); NFL builds
hit counts from `signals._stat_last10` at generation time. Control test —
how often each array position equals the prop's own `final_value`:

        pos 0  10.9%   pos 1  11.4%   pos 2  10.5%   pos 3  10.9%   pos 4  9.6%

Flat. A leak spikes position 0. Same-opponent matches ~0.5% at every
position (division rematches). `prop.week` is NULL on every NFL row — the
generator still writes `week=None` — so the week comparison was
unavailable and this control replaces it.

**MLB cannot be judged yet and its flattering numbers are the leak:**
post-09-22 PRIME n=29 and STRONG n=23 are both under the n=30 floor; the
pre-09-22 PRIME 74.5% (n=2,477) is the leak, not a record. The clean MLB
window is three days. `audit_prop_tier_ordering.py` prints the pre-fix
window marked NOT QUOTABLE rather than hiding it, because a window that is
merely omitted invites someone to recompute it later and believe it.

No thresholds changed — how to resolve it (re-cut bands, relabel, or stop
publishing the two losing tiers) decides what subscribers see.
